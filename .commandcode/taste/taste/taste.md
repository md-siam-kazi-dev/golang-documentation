# Taste
- Communicates in terse, informal shorthand with typos and minimal punctuation (e.g., "Read Prd.md ,also read sidebar.json for sidebar . create all route for sidebar", "some table content are not work properly . also implement terminal style where code exist"); expects the assistant to fill in the details by reading project files, diagnosing root causes, and inferring intent. Confidence: 0.9
- Wants demo/placeholder content scaffolded first so they can drop in the real content later ("add demo context now . I will add md file letter"). Prefers a working skeleton with clearly-marked placeholder bodies over waiting for final copy. Confidence: 0.7
- Prefers site routes/navigation to be driven from a config file (sidebar.json) via a re-runnable generator, rather than hand-maintaining each route/file individually. Confidence: 0.5
- Authors documentation content as plain Markdown files in a separate content folder (e.g., `public/doc/`), not directly as MDX in the site's content tree; expects the assistant to migrate/convert those files into the rendering pipeline (frontmatter, slug matching, section splitting) when wiring them in. Explicitly points the assistant at `public/doc/` when delivering new authored content ("i already added necessary md file in /public /doc") and expects the existing fundamentals-style transfer to be extended to the new section rather than hand-writing files. Delivers these files incrementally, in batches per section across successive rounds (first Fundamentals, then a few Core Programming topics, later the remaining core topics via "here alreay added file for go core . implement this"); each round the assistant should detect the newly added files and extend that section's transfer mappings so all sidebar topics get real content overwriting their placeholders. Confidence: 0.9
- When authored docs arrive with broken/lost markdown (e.g., pasted from plain text — bare `N. Title` lines instead of `## N. Title` headings, code snippets not in fenced blocks, even an unterminated ```go fence), prefers the assistant to repair the formatting in the source files and then transfer, rather than transferring broken markdown as-is or waiting for re-pasted files; wording must be preserved while structure is restored. Confidence: 0.7
- Their documentation content follows a consistent structure convention: numbered `## N. Title` H2 headings, code wrapped in ```go blocks and output/diagrams in ```text blocks, and a trailing `## Summary` (often plus `## Practice`); repairs and new content should match this format. Confidence: 0.6
- A later batch of their authored Go docs is written in an explicit teacher/lesson voice: an opening `## Introduction`, bold callouts labeled `Teacher note` / `Teacher Rule` / `Teacher warning` / `Teacher Exercise` (often as `>` blockquotes), and a closing `## Summary` frequently followed by a `### Mental Model` (or `### Final Mental Model`) diagram. These lesson-style headings/callouts should be preserved when repairing or extending this content, not normalized away. Confidence: 0.55
- Grants the assistant latitude to restructure their source content for a better site architecture — splitting combined files into separate pages, renaming/slugifying to match the sidebar, renumbering sections — rather than requiring 1:1 fidelity to the authored files. Confidence: 0.5
- Treats `public/sidebar.json` as the source of truth for topic slugs/page naming: content files must match the sidebar's expected filename/slug exactly (found a stale `custom-errors.mdx` vs sidebar topic "Custom Error" singular), and any drift is a defect to fix rather than something to accommodate. Confidence: 0.6
- Any text surfaced in the UI from generated meta (e.g., `description` shown in the prev/next bottom-nav cards) must be clean plain text — auto-derived descriptions need inline markdown (`**bold**`, `` `code` ``, `[link](url)`) stripped at generation time, never passed through raw. Confidence: 0.6

- Expects site-wide, per-page completeness for cross-cutting site features rather than a minimal subset — explicitly asked for SEO covering *every* page (per-page metadata plus sitemap and robots.txt), the same thoroughness they want for other infra like icons/branding. Confidence: 0.55
- Favors deep root-cause diagnosis that reproduces the reported bug in a real browser before fixing — for the mobile sidebar issue the assistant launched headless Chrome with CDP mobile emulation to measure the drawer's computed rect, discovered a `backdrop-filter` ancestor was the fixed-position containing block, and then re-verified the fix end-to-end (open drawer, scroll to last topic, click, navigate, and repeat at 320px) plus a full `tsc` typecheck. Wants fixes verified against the actual failure scenario, not just eyeballed. Confidence: 0.6

- Deploys/hosts the site on Vercel and wants Vercel's first-party platform tooling integrated into the project (e.g., asked to "Implement vercel analytics" via `@vercel/analytics`), wired at the root layout so it covers every page rather than a single route. Confidence: 0.5

- Wants a read-only audit before any code changes: inspect the whole project first, produce a concrete findings/plan document, and only implement once that's approved. Confidence: 0.6
- Strongly anti-spam and quality-first: never fabricate content to satisfy a requirement, never keyword-stuff, never create thin/duplicate pages competing for the same intent, and never delete useful pages or change existing URLs unnecessarily. Quality for real users matters more than the metric. Confidence: 0.65
- Wants honest reporting: do not invent numerical scores/metrics that weren't actually measured — say what couldn't be measured and why. Confidence: 0.6
- Expects a verification gate after implementation: run lint, type checking, and a build, then inspect the actual generated output (routes, sitemap, robots, canonicals, metadata, structured data, internal links) rather than assuming it works. Confidence: 0.6
- Wants changes scoped to the project's existing architecture and coding style — fix the targeted problem without rewriting unrelated parts of the app. Confidence: 0.55
- Expects a structured end-of-task report: what changed and why, files modified, files created, URLs/routes affected, remaining known issues, and recommended next steps. Confidence: 0.6
- Wants dependencies kept to a minimum: before adding a package, the framework's built-in capability must be checked, then whether the project already has an equivalent dependency, and only install if genuinely necessary. Confidence: 0.6
- Insists metadata/structured data (JSON-LD, titles, descriptions, dates, schema) describe only what is real and visibly present on the page — no fabricated dates, ratings, or reviews, and no schema for content that isn't there; would rather omit a field than fill it with a plausible-looking guess. Confidence: 0.6
- Prefers server-rendered content in Next.js: important text (docs, code examples) must not be gated behind client-only JavaScript, and the app should stay on Server Components unless client state is actually required rather than becoming one large Client Component. Confidence: 0.5
